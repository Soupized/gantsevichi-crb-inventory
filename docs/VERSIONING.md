# Правила версионирования

Проект использует [семантическое версионирование](https://semver.org/lang/ru/)
(SemVer) в формате `MAJOR.MINOR.PATCH`, например `1.4.2`.

## Что означает каждая часть

| Часть  | Когда увеличивается                                      | Пример                                      |
| ------ | -------------------------------------------------------- | ------------------------------------------- |
| MAJOR  | Несовместимые изменения API, базы данных или формата данных | `1.5.0` → `2.0.0`                          |
| MINOR  | Новая функциональность, совместимая со старой версией     | `1.4.2` → `1.5.0`                          |
| PATCH  | Исправления ошибок без новых возможностей                 | `1.4.2` → `1.4.3`                          |

Дополнительные обозначения:

- `1.5.0-rc.1` — кандидат на релиз;
- `1.5.0-beta.1` — тестовая версия;
- `v1.5.0` — формат тега в Git и на GitHub.

Начинать новый крупный проект с `0.1.0` допустимо, но для первой переданной
версии этого проекта используется `1.0.0`.

## Когда какая версия уместна

### PATCH — исправление

- исправлена ошибка в форме;
- исправлена опечатка в тексте;
- устранён сбой при сохранении;
- обновлена зависимость без изменения поведения.

Пример сообщения коммита: `fix: исправлено сохранение пустого объёма ОЗУ`.

### MINOR — новая возможность

- добавлен экспорт в Excel;
- добавлен новый тип устройства;
- добавлен фильтр по кабинету;
- добавлена страница с историей ремонтов.

Пример сообщения коммита: `feat: добавлен экспорт списка компьютеров в Excel`.

### MAJOR — несовместимое изменение

- изменён формат существующих полей API;
- удалён или переименован endpoint;
- изменена схема базы данных, требующая миграции;
- изменён способ авторизации.

Пример сообщения коммита: `feat!: изменён формат ответа API компьютеров`.

## Порядок выпуска версии

1. Убедитесь, что все изменения закоммичены и отправлены в GitHub.
2. Перенесите нужные пункты из раздела `[Не выпущено]` в новый раздел
   `CHANGELOG.md` с датой выпуска.
3. Определите новую версию по таблице выше.
4. Создайте коммит с версией:

   ```powershell
   git add CHANGELOG.md
   git commit -m "chore(release): 1.1.0"
   ```

5. Поставьте аннотированный тег:

   ```powershell
   git tag -a v1.1.0 -m "Версия 1.1.0"
   ```

6. Отправьте коммит и тег:

   ```powershell
   git push
   git push origin v1.1.0
   ```

7. На GitHub откройте **Releases → Draft a new release**, выберите тег `v1.1.0`,
   укажите заголовок и вставьте описание из `CHANGELOG.md`.
8. Опубликуйте релиз.

## Соглашение о коммитах

Используется упрощённый [Conventional Commits](https://www.conventionalcommits.org/ru/):

| Префикс     | Назначение                                      | Пример                              |
| ----------- | ----------------------------------------------- | ----------------------------------- |
| `feat:`     | новая функциональность                          | `feat: добавлен фильтр по кабинету` |
| `fix:`      | исправление ошибки                              | `fix: исправлена привязка монитора` |
| `docs:`     | документация                                    | `docs: обновлена инструкция запуска` |
| `chore:`    | обслуживание, зависимости, версия релиза        | `chore(release): 1.1.0`             |
| `refactor:` | переработка кода без изменения поведения         | `refactor: упрощён контроллер`      |
| `test:`     | тесты                                           | `test: добавлена проверка API`      |

Один коммит должен содержать одно логическое изменение. Сообщение пишется в
повелительном наклонении: «добавлен», «исправлено», «обновлено».

## Ветки

- `main` — стабильная версия; сюда попадает только проверенный код.
- `feature/краткое-название` — новая возможность.
- `fix/краткое-название` — исправление.

Для небольших правок допустимо коммитить напрямую в `main`, но для крупных
изменений лучше создавать отдельную ветку и Pull Request.

## Версия в README и интерфейсе

- актуальная версия указывается в начале `README.md`;
- при выпуске новой версии обновите номер в README;
- тег версии в Git должен совпадать с номером в README и `CHANGELOG.md`.

## База данных и совместимость

Изменение структуры базы данных — потенциально несовместимое изменение.
Перед обновлением:

1. сделайте резервную копию `server/library.db`;
2. проверьте приложение на копии базы;
3. при необходимости подготовьте миграцию EF Core;
4. укажите в `CHANGELOG.md` необходимость резервной копии и миграции.
